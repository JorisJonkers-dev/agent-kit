**How parallel nodes work (Gold Band, commit 987fc3e)**

**1. Static workflow mode: no parallelism.** DSL has only `Worker` and `AiDynamic` node types (src/dsl/mod.rs:233-237). Validation rejects two edges with the same `(from, on)` outcome — "node `X` already has a `success`/`failure` edge" (src/dsl/mod.rs:922-929) — so each node has at most one success and one failure successor (plus reserved `$end`/`$new-round`, mod.rs:14-16, 18-27). `decide_next_step` returns exactly one `TransitionToNode` per outcome (src/control/mod.rs:24, 66-75, 94-97). So fan-out/fan-in in the plain workflow DSL: **NOT FOUND**.

**2. All parallelism is inside an `ai-dynamic` node's dynamic graph.** Its `control` block (`DynamicControlDsl`, src/dsl/mod.rs:461-473) sets limits, defaults: `max_dynamic_nodes=20`, `max_fanout=5`, `max_depth=6`, `max_parallel=3`, `max_group_depth=1`, `max_workflow_invocations=10` (src/dsl/mod.rs:498-515); all must be positive (mod.rs:766-786).

**3. Fan-out.** A dynamic leaf's completion proposes `DynamicNext::End | Single | Fanout` (src/dynamic.rs:691-705). `Fanout` carries 2+ branch `DynamicNodeSpec`s plus mandatory `merge` and `acceptance` task specs (src/dynamic.rs:696-701). Schema forces `nodes` `minItems: 2` and `maxItems: max_fanout` (src/dynamic.rs:1172-1173); runtime rejects `dynamic.fanout.max-fanout-exceeded` when `nodes.len() > max_fanout` (src/app/orchestrator.rs:11427-11436) and consumes `max_fanout` from the node's control via the schema policy (orchestrator.rs:6133, 6090-6135). Each fanout requires a fixed clean source commit ("fanout requires a fixed source commit", orchestrator.rs:12209) and forks one isolated git worktree per branch node (`fork_dynamic_workspace_from_commit` loop, orchestrator.rs:12214-12221); branches share a `DynamicGroupState` recording `root_node_ids`, `merge`, `acceptance` (orchestrator.rs:12226-12255).

**4. maxParallel.** `refresh_dynamic_ready_nodes` promotes Pending nodes whose `depends_on` are all completed-success, but only while `available_slots = max_parallel − active_leaves > 0` (orchestrator.rs:12359-12390). So `maxFanout` bounds width of one proposal; `maxParallel` bounds how many leaves run concurrently at any time (queued branches wait for slots).

**5. Fan-in/merge.** When a group's terminal branches finish, `advance_dynamic_groups` checkpoints every child workspace and creates a `Merge` node in the group's target workspace with `depends_on = terminal_node_ids` — i.e., it depends on all branches (orchestrator.rs:12427-12460; node creation 12688-12736). Merge runs as an agent stage with the `ai-dynamic-merge` prompt (orchestrator.rs:9122-9128, 13362-13365), receiving predecessor attachments/contexts (orchestrator.rs:13616-13624, 14071-14126). On merge completion an `Acceptance` node is created `depends_on` the merge node (orchestrator.rs:12466-12478, 12740-12783; prompt 13366-13369). After the run ends, one `AiDynamicResult` artifact is written to the outer ai-dynamic attempt (orchestrator.rs:8304-8331), and the outer workflow's next node consumes it as the predecessor's output artifact (src/app/node_executor.rs:293-306, 398-435) — one combined result, one next node.

**6. Two different agents/models judging the same input in parallel?** Yes — but only via ai-dynamic fanout, never in the static DSL. `available_agents` gives each agent its own provider+model (+permission mode) per dynamic node (src/dsl/mod.rs:439-445, 425-438; `acceptance_model` mod.rs:432). Each branch `DynamicNodeSpec` picks its own `provider`/`model` (src/dynamic.rs:632-635, provider enum-validated by `dynamic_completion_schema_policy`, orchestrator.rs:6090-6135, and `dynamic_model_for_provider`, orchestrator.rs:5686-5697). Duplicate node ids are rejected but identical tasks are legal (orchestrator.rs:11474-11476) — so two branches can judge the same input with different providers, run in parallel (bounded by `maxParallel`), sibling outputs staying isolated ("parallel sibling; not an input dependency", orchestrator.rs:14023-14055; tests 21581, 21755), then be combined by the group merge+acceptance into a single subsequent node (`Single` after acceptance, orchestrator.rs:12072-12087) and finally into the outer workflow's one successor edge. AUTO mode simply hosts ai-dynamic orchestration (`ExecutionPlanRunMode::Auto`, src/execution_plan/model.rs:14-16, 43-47); parallelism itself is unrelated to it.

SUMMARY: Gold Band supports parallelism only inside `ai-dynamic` nodes. The static workflow DSL is strictly sequential: validation forbids two edges with the same outcome from one node (src/dsl/mod.rs:922-929) and control picks exactly one next node (src/control/mod.rs:24, 75, 94) — no fan-out exists there (NOT FOUND). Inside an ai-dynamic dynamic graph, the agent-proposed `next.type=fanout` creates 2..maxFanout branch nodes (default 5; src/dsl/mod.rs:501-503; schema minItems 2/maxItems max_fanout, src/dynamic.rs:1172-1173; runtime check orchestrator.rs:11427), each in its own forked git worktree (orchestrator.rs:12209-12221). Branches are grouped with mandatory `merge` (git checkpoints + merge node depending on all terminal branches, orchestrator.rs:12427-12460, 12688-12736) and `acceptance` (depends on merge, orchestrator.rs:12466-12478) stages; results fan in there and the run ends with a single `AiDynamicResult` artifact (orchestrator.rs:8304-8331) that the outer workflow's one successor node consumes (node_executor.rs:306). Concurrency is capped by `maxParallel` (default 3; src/dsl/mod.rs:507-509): only `maxParallel − active` slots get promoted (orchestrator.rs:12359-12390). Two different agents/models can judge the same input in parallel: branches carry per-node provider/model validated against the node's `available_agents` (src/dsl/mod.rs:439-445; orchestrator.rs:5686-5697, 6090-6135), sibling outputs are isolated ("parallel sibling; not an input dependency", orchestrator.rs:14023-40), and merge+acceptance combine them into exactly one next node. AUTO mode only hosts orchestration (execution_plan/model.rs:43-47); parallelism is an ai-dynamic feature, independent of run mode.
