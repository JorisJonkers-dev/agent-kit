## Problem Statement

Today the owner's three delegation loops — deep research, one-ticket implementation, and grilling an idea into tickets — are run by hand across several tools. Each loop has a part that trusts a model's word: a stage "passes" because the agent said so, not because a command ran; a repair loop ends when the agent stops rather than when a budget is spent; a citation is used without being checked against the page it came from.

Gold Band can sequence this work, but its DSL does not natively do any of it. It has no command or script node, so no stage can deterministically run `cargo test` and branch on the exit code. Its static workflow is strictly sequential — one success edge and one failure edge per node — so judges cannot run in parallel. It has no token, cost, time or spend limit at node or run level, and its token metrics are documented to have regressed to 0, so a runaway loop cannot be stopped by Gold Band itself. Node kinds are a closed enum with no plugin or hook system, and #327's decision is that Gold Band's Rust is not changed.

So the loops must be expressed with what exists — worker nodes judged by output contracts, back-edges bounded by `control.max_attempts`, dynamic fan-out and merge inside `ai-dynamic` nodes, and `manual_check` pauses resolved by a human — with small shims closing the gaps Gold Band cannot express. This spec says what the three workflows are, which agent ids fill which nodes at which reach level, where the money is capped, and how each workflow is proved headless with stub agents before any model is spent.

## Solution

Three Gold Band workflow definitions, reviewed as files and run headless or in the app, per the owner's direction that everything runs on Gold Band — the three new workflows first, the existing critique stages second, and the remaining skills later, in waves after an inventory. None of it changes Gold Band's Rust. Every gap Gold Band cannot express is closed by a shim: a cheap worker node plus a pinned wrapper script. New agent-kit code (the wrappers, validators and export logic) is Rust under the 7-day crate cooldown (standards ADR-0014), per the direction set in spec #327.

Deterministic gates — build, tests, lint, 100 percent line coverage on changed files, crate-age for Rust — run through a gate shim: a cheap worker whose agent id can only run one pinned wrapper, which writes a verdict JSON into a directory the gate agent cannot write, and a second read-only node that copies the verdict into its success condition and fails on mismatch. The model never authors the verdict.

Workflow A orchestrates deep research: Opus at the start and at acceptance, a planner stating sources and questions, fetchers fanned out across cheap models in one `ai-dynamic` node, cheap merge workers writing into a private research repo in the estate-kit-papers layout, and a read-only verifier checking quotes against fetched pages. Workflow B implements one ticket: a test author from a different model family writes failing tests first, one writer (Claude Sonnet) implements to green, gate-shim gates, then two judges in at least two non-writer families running in parallel inside one `ai-dynamic` node; failures loop back to the writer, capped at two repairs, then an Opus judgment node, then a human. Workflow C grills an idea to tickets entirely inside Gold Band, with `manual_check` at the grill rounds, on needs-human findings, and on ticket publication, and exports the published issue to `requirement.md` for Workflow B. Agents never need GitHub write reach.

Money is capped at the LiteLLM keys, not in Gold Band: per-key `max_budget` of 255 EUR on Vibe, 128 EUR on Vibe-study, 60 EUR on OpenCode Go. Claude on Max x5 is unmetered and is therefore kept to judgment nodes. Gold Band's own cost reporting is not relied on at all.

## Implementation Decisions

- **Direction.** Everything runs on Gold Band. The three new workflows are the first wave; the existing critique stages (/review-spec, /review-tickets, and the rest) are the second; the remaining skills — roles, skill sets, MCP servers, ACLs/reach levels, custom installs — port later, in waves, after an inventory of existing skills, hooks, roles and MCPs. Gold Band's Rust is not changed: node kinds are a closed enum (worker, ai-dynamic; src/dsl/mod.rs:216-219) and there is no plugin or hook system, so every gap is closed with shims — tiny cheap worker nodes plus pinned wrapper scripts. Facts used: a worker with output and success_condition is a judge; its failure edge may point to any earlier node; `control.max_attempts` bounds repairs, `control.max_rounds` bounds $new-round rounds; there is no generic per-node loop counter. The static DSL is sequential (one success and one failure edge per node; validation rejects a second edge with the same outcome, src/dsl/mod.rs:923-929), so all parallelism lives inside `ai-dynamic` nodes.
- **Gate shim.** A gate node is a cheap worker whose agent ids may run only one pinned wrapper (reach: run-one-command, sandbox-exec). The wrapper executes its command and writes a verdict JSON — command, exit code, output hash, timestamp — into a directory the gate agent cannot write (write-scoped to a gate-output directory distinct from the wrapper's own write scope). A second tiny read-only node copies that file into its success_condition artifact; a mismatch or a missing file fails the condition and routes on the failure edge. The model never authors the verdict. This exists because Gold Band has no command or script node and no exit-code concept at node level: a test or coverage run can otherwise only happen by trusting an LLM agent's report. How exactly a launcher config pins an id to a single command under the capability-profile mechanism of #327 — the sandbox profile shape, the wrapper binary name, the gate-output directory layout — is part of the first piece of work and is currently UNVERIFIED beyond the pattern itself.
- **Workflow A (deep research).** Orchestrated by Opus only at the start (a targeted prompt plus inputs) and at acceptance (the ai-dynamic acceptance model binding exists, `acceptance_model` src/dsl/mod.rs:432). A planner node states the source list and questions. One `ai-dynamic` node fans out fetchers — Pi with read-web reach, cheap models across the Vibe, Vibe-study and OpenCode Go keys via LiteLLM — up to maxFanout (default 5; branches get one isolated git worktree each, merge and acceptance nodes are mandatory, and the group produces one result artifact the next node consumes). Merge and organise: cheap workers write into the research repo in the estate-kit-papers layout — catalog.json as the single source of truth, a generated INDEX.md, notes/ and evaluations/ — with write scope limited to research/. The quote check and source-tier rules from the papers repo apply; a read-only verifier node checks quotes against the fetched pages. The maximum width and depth of the dynamic graph are declared explicitly in the node's control block rather than left at the defaults (defaults: maxDynamicNodes 20, maxFanout 5, maxDepth 6, maxParallel 3).
- **Workflow B (implementation, one ticket, from requirement.md).** Step 1: a test author from a model family different from the writer writes failing tests from the ticket's acceptance criteria first. Step 2: one writer only (Claude Sonnet) implements until the tests pass. Step 3: deterministic gates via the gate shim: build, tests, lint, coverage (100 percent lines on changed files), crate-age for Rust. Step 4: judges in parallel inside one ai-dynamic node: a code-quality judge and a tests-vs-spec judge, at least two judge families, each different from the writer's family (the brief's examples are GLM and DeepSeek; whether those families are reachable from Gold Band through LiteLLM at these keys is UNVERIFIED). Judges return findings in the finding schema as their output contract. Step 5: any failed judge or gate sends back to the writer with the critiques; the repair back-edge is budgeted by `control.max_attempts = 2`. When the budget is exceeded the run terminates as failure unless the last routing step avoids it, so the cap is expressed with explicit back-edges to the writer and a judgment step: after the second failed repair an Opus judgment node adjudicates, then a manual_check by the human decides. Back-edges point to earlier nodes, which validation allows (existence is the only check, src/dsl/mod.rs:875-881). Step 6: Opus is used only for judgment nodes — escalation and final acceptance. Invalid judge output already gets up to 3 hidden repair prompts from Gold Band itself (MAX_INVALID_OUTPUT_REPAIR_PROMPTS, orchestrator.rs:212) before failing; the workflow relies on that only for the finding-schema validation, not for the repair loop.
- **Workflow C (grill to tickets, all inside Gold Band).** The sequence is grill (a manual_check pause per question round) -> critique -> spec -> critique (review-spec equivalent) -> tickets -> critique (review-tickets equivalent) -> publish tickets and sub-issues. manual_check on: grill answers, needs-human findings, ticket publication. A worker with `manual_check` cannot also carry output/success-condition validation (src/dsl/mod.rs:~650), so each pause is its own worker node; in headless runs it pauses the run with exit code 2 and is resolved out-of-band in the app or over IM. The output feeds Workflow B: a wrapper exports the issue and its sub-issues to requirement.md, which is the file `gold-band run --requirement-file` consumes, so agents never need GitHub write reach.
- **Reach and skill sets.** Gold Band has no per-node skills, working directory or tool allow-lists (src/dsl/mod.rs:261-284, 445-455; skills are managed per agent directory, src/skill/mod.rs:17-25), so reach and skill sets are carried by one Gold Band agent id per (agent, reach level, skill set), exactly the id-per-profile mechanism #327 lands. The reach levels are: read, read-web, research (web plus scoped write), write-scoped, write, full, plus run-one-command for gates. Enforcement is two layers, per #327: tool configuration per agent id, and sandbox-exec at the operating system. Web access cannot be blocked at the OS layer (every agent needs the network to reach its model), so web limits are tool-config and MCP-list limits only, and the spec claims nothing stronger.
- **Budgets.** Gold Band has no token, cost, time or spend cap at node or run level (only the structural limits above), and its token metrics are documented to have regressed to 0 (docs/gold-band/fix-token-metrics-reporting.md; commit 2135ee9 hard-coded reported token counts to 0 in orchestrator metrics). Budgets are therefore enforced where money actually flows: LiteLLM per-key max_budget — Vibe 255 EUR, Vibe-study 128 EUR, OpenCode Go 60 EUR. Claude on Max x5 is not metered; Claude use is kept to judgment nodes. No workflow, wrapper or report relies on Gold Band's token or cost numbers. How LiteLLM's max_budget behaves over time (per key, per what window, what happens at the cap) is UNVERIFIED in these fact files and must be settled before the first real run.
- **Private research repo.** The research repository is private and separate; `research/` in the consuming repository is a git submodule of it. Private research papers may be read by any cheap worker; the owner accepted the provider exposure that implies. The papers repo's quote-check and source-tier rules apply to everything written into it, and the layout is estate-kit-papers: catalog.json single source of truth, generated INDEX.md, notes/, evaluations/.
- **Rust and crate cooldown.** New code — the gate wrappers, the verdict validators, the tickets-to-requirement.md export — is Rust under the 7-day crate cooldown (standards ADR-0014, followed as in #327: crate-gate resolves cargo commands, crate-age fails closed on any Cargo.toml or Cargo.lock change in the pre-commit hook and the pull-request workflow). The cooldown covers crates only; npm and PyPI packages are not part of it, per #327. The pinning of wrapper binary names to Gold Band agent ids is declarative and reviewed; the concrete names are open (below).
- **Port waves.** Wave 1: the three workflows in this spec. Wave 2: the existing critique stages as Gold Band workflow templates (building on #327's degraded critique-path work, which ships the spec-stage template; #327's list of guarantees lost on that path stays in force and is not restored here). Later waves: the remaining skills after the port inventory required by story 3; the design of those waves is not this spec. Gold Band gaps found on the way are recorded for possible upstream issues (command node, static fan-out, budgets); they are recorded, not fixed, here.

## Testing Decisions

- A good test checks behaviour a person would see: run states, exit codes, verdict files and exported requirement.md files. It does not check how the wrappers build them.
- **Seam 1 (main): headless run of each workflow against stub ACP agents.** Each of the three workflows runs headless through `gold-band run --requirement-file X --workflow J` with a fixture stub ACP agent standing in for every named agent id, so no model and no network is needed. The test asserts the canonical RunState and the exit code: 0 for success, 2 for the paused manual_check nodes (Workflow C's grill rounds, needs-human findings, publication; Workflow B's escalation), 1 for failure runs. It asserts routing: Workflow B's failure path returns to the writer node, the second failed repair reaches the Opus judgment node, and the repair cap terminates the run with `workflow_control_limit_exceeded` when exceeded. It is skipped, with an explicit reason, when no headless Gold Band binary is supplied by the environment, matching #327's build of that binary from the audited source through crate-gate.
- **Wrapper unit tests.** The gate wrappers and the export wrapper are Rust and carry unit tests in their crate: a green command, a failing command and a command that cannot run each produce the expected verdict JSON (command, exit code, output hash, timestamp); the export wrapper converts a fixture issue and sub-issues into requirement.md.
- **Verdict mismatch must fail.** Dedicated tests tamper with the gate seam: a missing verdict file, a verdict file whose content does not hash-check, and a verdict signed for a different command must each end the run in failure through the read-only copier's success_condition. This is the property that makes the shim honest, so it is tested at the seam, not assumed.
- **Coverage on changed files.** 100 percent line coverage on changed files applies to the new Rust code (wrappers, validators, export), the same gate Workflow B itself enforces on tickets; the coverage tool is named when the crate is chosen (per #327, for example cargo llvm-cov).
- **Crate age.** crate-age runs over the agent-kit workspace lockfile in the pre-commit hook and in the pull-request workflow, covering the new wrappers' crates.
- Prior art: #327's headless workflow-run seam for the critique spec-stage template, its stub-agent fixture pattern, and the registry-validation tests.

## Out of Scope

- Any change to Gold Band's Rust, including the ideas recorded as possible upstream issues (command node, static fan-out, budgets); they are recorded for the owner, not implemented.
- Replacing the critique runner, the council or the model gateway; the lost-guarantee list from #327 is not restored here.
- Enforcing the Codex ban, secret handling, sandbox profiles or capability profiles themselves: those land in #327 and are consumed here.
- Enforcing cost limits inside Gold Band or repairing its token metrics; budgets live at the LiteLLM keys.
- The designs of the later port waves beyond the second; the port inventory (story 3) produces the input for those designs, it does not produce them.
- Changes to the estate-kit-papers layout or the quote-check and source-tier rules; Workflow A conforms to them.
- A cooldown for npm and PyPI packages (per #327 they stay pinned, without install scripts).
- Giving any agent GitHub write reach; the export wrapper is the only path from Workflow C to Workflow B.
