## Problem Statement

The owner's skills, roles, hooks and MCP servers live today as files for other harnesses. They are installed into the Claude Code and Codex homes, they work by convention, and their special behaviour — special considerations, special ACLs, custom installs — exists only as prose in skill files and repo layouts. The owner wants all of them ported into workflows, dynamic workflows, custom roles, skill sets and MCP servers structured around Gold Band, and wants all previous specs and parts done for Gold Band.

Two Gold Band facts shape the whole port. First, Gold Band has no plugin or hook system and no runtime-extensible node types: the node set is a closed enum of worker and ai-dynamic (src/dsl/mod.rs:216-219; src/domain/mod.rs:24-28), and there is no hook module anywhere in `src/`. So a hook cannot be ported to Gold Band at all — it can only stay outside. Second, Gold Band has no per-node skills, working directory or tool allow-lists (src/dsl/mod.rs:261-284, 445-455); skills are managed per agent directory (src/skill/mod.rs:17-25). So a skill cannot be attached to a workflow node; it has to ride on a Gold Band agent id, and so does every ACL.

The surface is also uneven. Some skills are interactive (grill, brainstorm) and Gold Band's only human seam is `manual_check` (a worker carrying manual_check cannot also carry output validation, src/dsl/mod.rs:~650; headless runs pause with exit code 2 and are resolved out-of-band). Some skill behaviour assumes loops Gold Band cannot express — there is no generic per-node loop counter, only `control.max_attempts` and `control.max_rounds`. And skills span two homes (skills/workstation and skills/repo) with overlapping older issues attached to them, so a careless port would port the same thing twice or drop one.

So the port needs an inventory where every skill, hook, role file and MCP server gets exactly one target — a workflow, a role, a skill set, an MCP server, or "stays outside" — and waves cut from that inventory. This spec says how the port is cut: the target rule, the reach and skill-set structure, the wave order, what stays outside, which older issues it overlaps, and how each ported workflow is proved headless with stub agents before any model is spent.

## Solution

Ticket #351 builds the inventory of every current skill, hook, role file and MCP server. This spec cuts the waves from it. Every inventory row gets exactly one target: a Gold Band workflow definition, a role, a skill set, an MCP server registration, or "stays outside". Nothing gets two targets and nothing gets none. The port runs in waves: the three delegation workflows are Wave 1 and are done in #350; the critique stages are Wave 2 (#363) and run on the critique runner, which stays the executor and keeps its guarantees — read-only proof, packet confinement, timeouts; the remaining waves are cut from the #351 inventory.

Everything runs on Gold Band. Gold Band's Rust is not changed. Every gap Gold Band cannot express is closed with a shim: the gate wrapper from #350, one agent id per reach level and skill set, and unrolled loops where a skill assumes a loop the DSL cannot count. Skill sets are installed per Gold Band agent id, because Gold Band writes skills per agent directory and not per node. ACLs are the seven reach levels — read, read-web, research, write-scoped, write, full, run-one-command — enforced by two layers: per-agent tool configuration and sandbox-exec. Web access cannot be blocked at the operating-system layer, and the spec claims nothing stronger.

Hooks and plugins stay outside: Gold Band has none, so hooks stay in the Claude Code and Codex homes where they run today. Opus is used in judgment nodes only. Codex is banned, with no OpenRouter and no opencode/ Zen models, in every binding this spec produces. New code — the inventory check script, the registry validator, any port wrappers — is Rust under the 7-day crate cooldown (standards ADR-0014). Each ported workflow is proved by a headless Gold Band run against stub ACP agents before any real run.

## Implementation Decisions

- **Direction.** Everything runs on Gold Band. The owner's direction is to port all skills, with new special considerations, special ACLs and custom installs, into workflows and dynamic workflows on Gold Band — custom roles, skills, MCP servers and more, all structured around Gold Band — and to have all previous specs and parts done for Gold Band. Wave 1 (the three workflows) is done in #350 and is not re-cut here. Gold Band's Rust is not changed: node kinds are a closed enum (src/dsl/mod.rs:216-219) and there is no plugin or hook system, so every gap is closed with shims — the gate wrapper, one agent id per reach level and skill set, and unrolled loops. Opus is used in judgment nodes only; Codex is banned, with no OpenRouter and no opencode/ Zen models, in every binding. Dependencies hold in one direction: #327 says what exists and who may hold it, #350 says what runs on it, this spec says how the rest of the surface ports onto both.
- **Targets per item.** Each current skill, hook, role file and MCP server gets exactly one target: workflow, role, skill set, MCP server, or stays outside. The concrete mapping of each item is decided from the #351 inventory and recorded there; this spec fixes the rule, not the mapping (the per-item mapping is UNVERIFIED until #351 lands). A role target becomes a Gold Band managed agent with its capability profile (the managed-agent seam is `ManagedAgentConfig`/`ManagedAgentId`, src/provider/mod.rs:8-10); how a role file is represented exactly in Gold Band configuration is UNVERIFIED beyond that seam. An MCP server target is registered through Gold Band's MCP manager, which persists server config into settings.json with stdio/http/sse transports and deliberately leaves process management to the agent side (src/mcp/mod.rs:1-11, 63-69). A skill set target is a set of skills installed in one agent id's skill directory (src/skill/mod.rs:17-25, 36-42). A workflow target is a workflow definition file like the ones #350 lands. Where a skill's behaviour needs a deterministic command, it ports as a workflow with a shim (the #350 gate wrapper pattern), not as trusted skill text.
- **Skill sets and reach.** Skill sets are per Gold Band agent id, because Gold Band writes skills per agent directory and has no per-node skills field (src/dsl/mod.rs:261-284, 445-455; src/skill/mod.rs:17-25). This is exactly the one-agent-id-per-(agent, reach level, skill set) mechanism #327 lands, and this spec consumes it unchanged. The reach levels are read, read-web, research, write-scoped, write, full, plus run-one-command for gate wrappers. Enforcement is two layers: per-agent tool configuration and sandbox-exec at the operating-system layer. Web access cannot be blocked at the OS layer (every agent needs the network to reach its model), so web limits are tool-configuration and MCP-list limits only. Custom installs land in the per-agent directories Gold Band manages; the exact install layout for skills, roles and MCP servers is UNVERIFIED beyond the skill module's global/project management (src/skill/mod.rs:36-42).
- **Waves.** Wave 1: the three delegation workflows, done in #350. Wave 2: the critique stages (#363) as Gold Band workflow templates, on the critique runner, which stays the executor and keeps its guarantees — read-only proof, packet confinement, timeouts. The remaining waves are cut from the #351 inventory: each later wave is a recorded, ordered group of inventory rows with their targets, and no row enters a wave without its single target decided. The order after Wave 2 is an open question (below) and is settled before Wave 3 starts. Gold Band gaps found on the way are recorded for possible upstream issues (command node, static fan-out, budgets), not fixed here.
- **Interactive skills.** Interactive skills (grill, brainstorm) have no interactive node to port to; Gold Band's only human seam is `manual_check`, which pauses the run (headless: exit code 2) and is resolved out-of-band in the app or over IM (src/dsl/mod.rs:282, ~650; src/app/mod.rs:~6019). How these skills map — as manual_check-driven workflows or as stays outside — is an open question the owner listed, so no mapping is decided here (UNVERIFIED). Such a skill gets no target and enters no wave until its mapping decision is recorded.
- **Stays outside.** Hooks and plugins stay outside: Gold Band has none (no plugin/hook modules in `src/`, node set a closed enum), so hooks stay in the Claude Code and Codex homes and are recorded as "stays outside". Nothing in any wave expects a hook to fire inside a Gold Band run. Anything else the inventory marks stays outside keeps running where it runs today; the inventory record is the single place that says so.
- **Overlapping older issues.** #285 (research delegation) is Workflow A in #350 and is not re-ported here. #198 (hooks) stays outside. #24 (review harness) is Workflow B in #350. The wider open-issue sets — estate skills #285-#292, critique pipeline #167/#181/#182/#214 and children — get their resolution through the inventory rows of the skills they describe; critique-pipeline rows are Wave 2 (#363), and how the remaining estate-skill issues resolve is UNVERIFIED pending #351. Each overlap is recorded in the inventory as resolved by a named target or stays outside, so no issue is closed twice.
- **Rust and cooldown.** New code — the inventory check script, the registry validator, any port wrappers — is Rust under the 7-day crate cooldown (standards ADR-0014, followed as in #327 and #350: crate-gate resolves cargo commands; crate-age fails closed on any Cargo.toml or Cargo.lock change in the pre-commit hook and the pull-request workflow). The cooldown covers crates only; npm and PyPI packages stay pinned without install scripts, per #327.

## Testing Decisions

- A good test checks behaviour a person would see: the exit code of the inventory check, run states and exit codes of headless runs, and the pass/fail of registry validation. It does not check how the tooling builds those things.
- **Seam 1 (main): headless gold-band run of each ported workflow against stub ACP agents.** Every ported workflow — the Wave 2 critique-stage templates and each later-wave workflow — runs headless through `gold-band run --requirement-file X --workflow J` with fixture stub ACP agents standing in for every named agent id, so no model and no network is needed. The test asserts the canonical RunState and the exit code: 0 for success, 2 for paused `manual_check` nodes, 1 for failure (exit 3 is the CLI command itself failing and 4 is not-settled; neither is a workflow outcome, src/cli/mod.rs:89-106). It asserts routing on the seams the port adds: a workflow with repair back-edges returns to the earlier node on failure, and exceeding `control.max_attempts` ends the run with `workflow_control_limit_exceeded`. It is skipped, with an explicit reason, when no headless Gold Band binary is supplied by the environment, matching #350's build of that binary from the audited source through crate-gate.
- **Seam 2: inventory check script.** The Rust inventory check script reads the #351 inventory record on one side and the on-disk skills directories (skills/workstation, skills/repo), hook files, role files and MCP server configs on the other, and exits non-zero with a list of offenders unless every item appears exactly once with exactly one target and every recorded target points at something that exists — a workflow file, an agent id, a skill set, an MCP server entry, or the literal "stays outside". A person sees the list of unassigned or double-assigned items and the exit code.
- **Seam 3: registry validation.** A validator checks the port registry before any run: every agent id bound in a ported workflow exists with the declared reach level and skill set; every skill in a skill set exists in that agent id's skill directory (the per-agent layout of src/skill/mod.rs); every MCP server config parses into the settings.json shape Gold Band's MCP manager persists (src/mcp/mod.rs:63-69) and is listed only for agent ids whose reach level allows it. The exact registry file format is UNVERIFIED — the validator pins it when the first wave lands, and the test then checks the pinned format.
- **Wrapper unit tests.** Any new port wrapper is Rust and carries unit tests in its crate: a green case, a failing case and a case that cannot run each produce the expected output, in the pattern of #350's gate-wrapper tests.
- **Coverage on changed files.** 100 percent line coverage on changed files applies to the new Rust code (inventory check, registry validator, wrappers), the same gate Workflow B enforces on tickets; the coverage tool is named when the crate is chosen (per #327, for example cargo llvm-cov).
- **Crate age.** crate-age runs over the agent-kit workspace lockfile in the pre-commit hook and in the pull-request workflow, covering the new crates.
- Prior art: #350's headless workflow-run seam and stub-agent fixture pattern, and #327's registry-validation tests.

## Out of Scope

- Any change to Gold Band's Rust, including the gaps recorded as possible upstream issues (command node, static fan-out, budgets); they are recorded for the owner, not implemented.
- The design and build of the inventory itself: that is #351. This spec consumes the inventory and cuts the waves from it.
- The three delegation workflows (#350) and the critique-stage templates (#363); this spec ports onto them, it does not re-specify them.
- Replacing the critique runner, the council or the model gateway; the critique runner keeps its guarantees and stays the executor.
- Enforcing the reach levels, capability profiles, sandbox-exec or the Codex ban themselves: those land in #327 and are consumed here.
- Making hooks run inside Gold Band: there is no hook system to run them on. Hooks stay outside by fact, not by choice.
- Deciding the interactive-skill mapping and the wave order after Wave 2; both are open questions and are settled before the waves they affect.
- Cost enforcement inside Gold Band or repairing its token metrics; per #350 budgets live at the LiteLLM keys.
- A cooldown for npm and PyPI packages (per #327 they stay pinned, without install scripts).
